## 시그니처

## acquireRun 알고리즘 (결정 D2)
1. `mkdirSync(dir, {recursive:true})`; `tmp = runJson + ".tmp-" + process.pid`에 JSON 쓰기.
2. `linkSync(tmp, runJson)` 시도 → 성공: unlink tmp, return true.
3. EEXIST: `existing = readRun()`. `isRunLive(existing)`이면 unlink tmp, return false.
4. stale: `renameSync(runJson, runJson + ".stale-" + process.pid)` 시도 — 실패(ENOENT 등)면 다른 프로세스가 회수 중 → 2단계 1회 재시도 후 실패면 false. 성공: stale 파일 unlink → 2단계 재시도 1회 → 결과 반환.
- `isRunLive`: `process.kill(pid, 0)` ESRCH → false; EPERM → 살아있는 것으로 간주 후 ps 확인; `psArgs(pid)`(기본: `execFileSync("ps", ["-o","args=","-p",String(pid)])`, 실패 시 null)가 문자열이고 `--run-id <runId>`를 포함하지 않으면 false(pid 재사용). null(ps 실패)이면 pid 생존만으로 true.

## 테스트 케이스
1. acquire 2회(같은 프로세스 pid, run-id A 그리고 B, psArgs가 `--run-id A` 반환) → 두 번째 false.
2. 죽은 pid(999999)의 run.json을 미리 써두고 acquire → true(회수), 파일 내용이 새 run.
3. 살아있는 pid(process.pid)이지만 psArgs가 다른 run-id 문자열 반환 → stale로 회수 true.
4. releaseRun: pid가 다르면 삭제 안 됨; 일치하면 삭제.
5. appendEvent/readEvents 왕복, ts ISO, 다른 runId 이벤트 미포함.
6. pruneRuns: runs/ 7개 생성(이름 사전순=시간순) → 오래된 2개 삭제, 반환 목록 일치.
7. atomicWrite: 기존 파일 inode가 바뀐다(`statSync().ino` 비교), mode 0o755 지정 시 실행 비트.
